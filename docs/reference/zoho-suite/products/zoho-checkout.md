# Zoho Checkout Master Research Dossier

**Document ID:** GH-ZOHO-CHECKOUT-KB  
**Program:** GH Real Estate / Sylvara systems knowledge base  
**Research cutoff:** 2026-07-20  
**Source policy:** Current official Zoho Checkout help/FAQ documentation only  
**Evidence labels:** `DOC-VERIFIED`, `LIVE-METADATA REQUIRED`, `VOLATILE`, `POLICY INPUT REQUIRED`, `RESEARCH INFERENCE`, `DOC-GAP`, `LEGACY DOC`

> **AI ingestion directive.** Zoho Checkout is a hosted payment-page product, not Zoho Payments' REST API, Zoho Billing's subscription engine, or Zoho Books' ledger. The current public Checkout documentation reviewed does not publish a general Checkout REST API. Never invent one. Use documented page configuration, hosted-page URLs and query prefilling, embed/link/QR surfaces, native integrations, exports/backup, and the configured gateway. Before any implementation, resolve legal entity, Checkout organization, page ID/status, gateway, page currency, purpose/payment mode, Books organization/account, tax/coupon/custom-field configuration, and current tenant UI. Treat all payer input and URL parameters as untrusted.

## 1. System boundary and selection rule

`DOC-VERIFIED` Checkout lets staff build reusable branded hosted payment pages for goods, services, or contributions. Pages can collect one-time or simple recurring payments, use a fixed or payer-entered amount, quantity, taxes, coupons, billing/shipping/contact/custom fields, terms/license consent, CAPTCHA, thank-you/redirect behavior, and a configured online payment gateway. Pages can be shared by direct link, QR, embed code/button, and supported social channels.

Checkout is **not**:

- the underlying payment processor or payout system;
- a general accounting ledger, bank reconciliation system, or revenue-recognition engine;
- a complete subscription lifecycle engine for trials, amendments, usage, proration, complex dunning and portal metrics;
- proof of payment from browser redirect alone;
- a secure store for card/bank data;
- an API-backed operational database.

### 1.1 Product choice

| Need | Use | Reason |
|---|---|---|
| Business-user-configured reusable public payment page | Checkout | Declarative page, sharing, coupons/taxes/custom fields and gateway collection |
| Complex recurring/hybrid billing | Billing | Plans/addons/trials/proration/metering/dunning/subscription lifecycle |
| Custom payment UX/API, saved methods, processor webhooks and payouts | Payments | Processor REST API and verified transaction lifecycle |
| Accounting invoices/payments/credits/reconciliation | Books | Financial system of record |

`RESEARCH INFERENCE` Checkout may coexist with Billing/Payments/Books, but coexistence is not automatic ownership. Define which product creates the invoice, subscription, payment, credit/refund and customer communication. Prevent the same event from being created twice.

## 2. Public integration surface and API gap

### 2.1 Documented machine-facing surfaces

- Hosted-page URL generated by Checkout.
- Link, QR, iframe/embed code and embed button.
- Query-string prefilling for documented customer/address/quantity/coupon/amount/custom fields.
- Native integrations, including Zoho Books and supported gateways such as Zoho Payments.
- Reports, CSV exports and organization backup.

`DOC-GAP` No general CRUD REST API for Checkout pages/payments/refunds was found in the official public Checkout documents reviewed as of the cutoff. An invoice custom field's “API Field Name” is documented for URL prefilling; it is not evidence of a general REST endpoint. If automation beyond these surfaces is required, use a supported connector/product API or obtain written current Zoho documentation—never reverse engineer private web endpoints.

### 2.2 Identifiers to persist

Maintain a sanitized tenant/page registry:

- `legal_entity`
- Checkout organization/account reference
- environment/use class
- page name and immutable page identifier/hosted URL
- page purpose, payment mode, amount rule, quantity rule and currency
- configured gateway/account
- Books organization/account integration mapping if joined
- tax/coupon/custom-field schema version
- expected return/redirect domain
- owner, approver, live/draft/inactive/expired status and last verified date.

Do not route by page display name or user-supplied organization/gateway.

## 3. Payment-page configuration model

### 3.1 Purpose, product and amount

- Purpose: product or contribution.
- Product type: goods or services where applicable.
- Amount: fixed or “customer decides.” A customer-decides page can set a minimum.
- Quantity preference can allow payer-selected quantity.
- Currency is a page/organization configuration and must be supported by the gateway.
- Payment mode: one-time, recurring, or page configuration that allows choice at checkout where supported.

`POLICY INPUT REQUIRED` Page name, product/service description, amount/minimum, quantity, contribution wording, currency and refund terms are approved business/legal inputs. Never expose rent, deposit, application fee, utility, penalty or other charge solely because Checkout supports an amount field.

### 3.2 Page lifecycle and sharing

Documented page states include Live, Inactive, Draft, and Expired. Expiry can be never, fixed date, or after a transaction count. Sharing surfaces include link, QR, embed code/iframe, embed button and selected social networks.

- Treat moving Draft/Inactive to Live as a production deployment.
- Deactivate/expire a page as the kill switch; test links and embedded copies after the change.
- Inventory every place a page URL/embed exists before replacement.
- Never assume changing Checkout removes cached/copied public links.

### 3.3 Customer fields and presentation

Pages can collect or display:

- first/last name, email, company, phone/mobile, website;
- billing and shipping addresses;
- card-address fields as supported by the gateway;
- invoice custom fields;
- terms/privacy links, license/consent checkbox and CAPTCHA;
- thank-you message or return/redirect URL.

Use the minimum required fields. Never collect application/tenant information, SSNs, IDs, bank/card credentials, lease documents or sensitive notes in a payment page/custom field.

## 4. Recurring Checkout model

Checkout supports simple recurring pages with documented frequencies such as weekly, monthly, quarterly, semiannual, annual and custom; billing day can follow checkout date or a selected day; duration can be unlimited or limited cycles. A page can optionally let a payer choose supported frequency/day/duration.

Statuses documented for recurring payments include Live, Future, Past Due, Canceled, Unpaid and Expired. Management can include customer/card update, renewal-date change, immediate cancellation or cancellation at next renewal (`Non Renewing`).

`DOC-VERIFIED` Retry settings can attempt failed recurring collection up to three times on configured intervals with email notifications. After attempts, the configured final state can be Unpaid or Cancelled.

Important limitations/controls:

- Current Checkout help warns that changing a renewal date does not automatically charge/prorate the displaced period.
- A browser/redirect cannot prove renewal success.
- Gateway, region, method and plan govern recurring support.
- Checkout recurring is not a safe substitute for Billing when proration, lease/service amendments, usage, trials, consolidated invoices, sophisticated dunning or revenue reporting matter.

`POLICY INPUT REQUIRED` Renewal day, duration, retries, notices, final state and consequences of failed payment require approved policy.

## 5. Coupons, tax, and currency

### 5.1 Coupons

- Percentage or flat discount, including documented 100% discounts.
- Redemption can be one-time, forever or a limited number of cycles.
- Optional expiry and maximum redemptions.
- Tax is calculated after discount according to current help.

Never allow arbitrary `coupon_code` without server/page rules. Discounts, concessions, waivers and promotions need authorization, effective dates and audit.

### 5.2 Taxes

Checkout pages can be taxable, non-taxable with exemption, or out-of-scope. Current US tax settings include rates, authorities and groups. A tax-enabled page is inaccessible until a default tax exists; the first created tax can become default.

`POLICY INPUT REQUIRED` Checkout is not tax advice. Finance/legal must supply jurisdiction, taxability, exemption, authority, rate/effective date and Books/Billing mapping. Tax changes can propagate to Finance apps/transactions, and used taxes may not be deletable. Prefer approved version/effective-date replacement to casual mutation.

### 5.3 Currency and gateway capability

Organizations can configure base and additional currencies with code, symbol, name, decimal precision and format. Exchange rate can be manually set or sourced through the documented Open Exchange Rates option. The configured gateway must support the page currency.

Do not conflate:

- displayed page currency;
- gateway charge currency;
- processor settlement currency;
- Books base currency and exchange-rate posting.

Reconcile all four where relevant.

## 6. Invoice custom fields and validation rules

Documented invoice custom-field data types include Text, Email, URL, Phone, Number and Date. Fields can be shown/required on hosted pages and displayed on transaction PDFs. Privacy settings can identify sensitive PII/ePHI; protected fields do not support some defaults/advanced search behavior.

Each field exposes an “API Field Name” used as the query parameter key for prefill.

Validation rules can contain multiple criteria/subrules and block saving/checkout. Use them as customer-input guardrails, not as the only authorization boundary. Validate again in the owning server/workflow before fulfillment.

`LIVE-METADATA REQUIRED` Capture field label, API Field Name, type, required/display/privacy/default/rule behavior and schema version from the tenant. Never guess an API Field Name from the label.

## 7. Hosted-page URL prefilling

### 7.1 Documented parameters

Hosted URLs use a `zohosecurepay.com/checkout/...` form. Official FAQ documents parameters including:

| Category | Parameters |
|---|---|
| Commerce | `quantity`, `coupon_code`; `amount` for customer-decides pages |
| Identity | `first_name`, `last_name`, `email`, `company_name`, `phone`, `mobile`, `website` |
| Billing | billing street/street2/city/zip plus `state_code` or state and `country_code` |
| Shipping | corresponding shipping address parameters |
| Custom fields | the field's exact API Field Name |

- Date custom-field format: `YYYY-MM-DD`.
- US/Canada/India/UAE examples use two-letter state code; country uses ISO alpha-2.
- Multiple parameters use `&`; values must be URL-encoded.
- A customer-decides page supports `amount`; a fixed-amount page cannot be overridden through the URL.

### 7.2 Security rules

- Every prefilled value remains untrusted; Checkout must validate it against the live page.
- Do not include card/bank data, OAuth/API/gateway secrets, tenant documents, internal roles or authorization claims.
- PII in URLs leaks through browser history, analytics, logs, referrers, screenshots, email and chat. Minimize prefill; prefer an opaque non-sensitive reference if an approved field exists.
- Use a server-generated, allowlisted link; never concatenate raw user data without strict encoding.
- A coupon/amount/quantity in the URL is not authorization for a charge or discount.

## 8. Gateways, payment state, refunds, and reports

### 8.1 Gateway boundary

Current US Checkout help lists streamlined gateways including Zoho Payments, Stripe, PayPal and Verifone. Older/global FAQ can show a broader legacy/edition matrix. `VOLATILE`: verify current tenant UI, region, method, currency, recurring and refund support before design.

When Zoho Payments is configured, Checkout remains the page and Zoho Payments remains the processor. Maintain page -> gateway -> processor account -> legal entity mapping.

### 8.2 Payment and refund state

Checkout payment statuses include Success, Unpaid, Refunded, Partially Refunded and Void in current help. Full/partial refunds depend on gateway support; official help commonly quotes three to five business days for return. Checkout creates a credit note as part of its refund workflow.

Controls:

- Never fulfill from thank-you page, redirect, browser screenshot or email alone.
- Verify the gateway/Payments event and retrieve current transaction where API exists.
- Match legal entity, page, amount, currency, payer/reference and transaction ID.
- Refund only an approved transaction and remaining amount; serialize; confirm processor and Books credit/refund treatment.
- Do not issue refund independently in Checkout and gateway/Payments.

### 8.3 Reports/export/backup

Checkout reports can export the first 10,000 rows. For more, official help directs users to data backup. Backup is compressed CSV; it can be initiated once every 15 days, download link expires after 30 days, and email generation may take about 30 minutes.

Backups/exports contain financial and personal data. Store in approved controlled storage, not GitHub; encrypt, restrict, retain/delete under policy and validate row counts/checksums.

## 9. Zoho Books integration and tenant hazard

Official FAQ documents connecting Checkout to Zoho Books and then selecting an account on a page. The integration can join/merge organization context.

Before connecting:

1. Resolve legal entity and Books `organization_id`/account owner.
2. Inventory Checkout pages, existing transactions, customers, currencies, tax and gateway.
3. Confirm whether connection joins shared Finance data and its reversibility.
4. Select approved Books income/clearing/liability account; `POLICY INPUT REQUIRED`.
5. Test with a nonproduction organization or approved canary.
6. Reconcile page payment, gateway transaction/refund/fees/payout and Books transaction.

Never connect GH and Sylvara across entity boundaries or choose an account by display name.

## 10. GH/Sylvara-safe workflow patterns

### 10.1 Application, reservation, deposit, or approved one-time charge

1. CRM/Creator approves event, legal entity, immutable operation key, amount/currency and charge type.
2. Server selects a registry-approved live Checkout page and emits a minimally prefilled URL.
3. Persist operation key + page/legal entity + expected amount/currency; no payment credentials.
4. Payer completes gateway-hosted flow.
5. Verified processor webhook/API state—not redirect—must match expectation.
6. Books creates/links the approved invoice/payment/clearing or liability record.
7. Update CRM/Creator by immutable cross-references and append audit status.

`POLICY INPUT REQUIRED` Deposit, rent, fee, contribution and reservation payments have different legal/accounting rules. Checkout page purpose does not decide treatment.

### 10.2 Simple recurring collection

Use Checkout only after accepting its frequency/retry/cancellation/proration limits. For governed lease/service amendments, trials, complex dunning, usage or revenue schedule, Billing should own subscription lifecycle and Checkout should not create a competing recurring instruction.

### 10.3 Refund

- Authorized request/ticket with payment/page/legal entity and reason.
- Retrieve gateway transaction; calculate remaining refundable; dual approval above threshold.
- Lock operation; submit once in the single owning system.
- Wait for verified processor state; reconcile Checkout credit note and Books credit/refund.
- Update operational state after financial confirmation.

## 11. Security and operational controls

- Separate GH/Sylvara Checkout organizations/pages/gateways/Books accounts where legal entities differ.
- Least-privilege users; periodic page/gateway/user review; owner/admin MFA.
- Do not copy gateway credentials, payment data, export data, page-management URLs or secret query values to GitHub.
- HTTPS return URLs; allowlisted domains; CSP/frame policy for embeds; test mobile/accessibility.
- CAPTCHA and page validation help with abuse, but use gateway fraud controls, rate/velocity monitoring and exception review.
- Log page ID, operation key, expected amount/currency, processor IDs, status transitions and reconciliation result; mask PII.
- Monitor page status/expiry, link failures, currency/gateway mismatch, duplicate operations, recurring Past Due/Unpaid, refunds and unmatched Books entries.

## 12. Testing and change control

Test matrix:

- fixed vs payer amount, minimum and quantity;
- valid/invalid/expired/100% coupon and tax-after-discount;
- all field types, mandatory/privacy/validation rule, URL encoding and malicious input;
- billing/shipping country/state formats;
- card/ACH/other supported gateway methods and currency combinations;
- one-time/recurring, retries, Future/Past Due/Unpaid/Non Renewing/cancel;
- return/redirect tampering, abandoned flow, duplicate submission;
- full/partial/duplicate refund and Books reconciliation;
- inactive/draft/expired page, copied embed/link and kill switch;
- reports 10,000-row boundary and backup controls.

Every page/configuration change is versioned production change: requirement/owner, screenshots/sanitized schema, affected pages/embeds, proposed state, security/accounting approval, canary, rollback/deactivation, and post-change reconciliation. Never edit a live page's amount/tax/gateway/recurrence without impact review.

## 13. Live-metadata checklist

- legal entity, region/edition, Checkout org and users;
- page IDs/URLs/statuses, purpose, product/service, amount/quantity/recurrence/expiry;
- gateway and processor account/currency/method/refund capability;
- Books integration organization/account and transaction mapping;
- currencies/exchange source, taxes/groups/authorities/exemptions;
- coupons and redemption rules;
- standard/custom fields, API Field Names, privacy, validation and PDF visibility;
- terms/privacy/license/CAPTCHA and return/thank-you behavior;
- embeds/links/QR inventory, reports/backup owner and retention;
- approved event/payment/refund/reconciliation workflows and monitoring.
